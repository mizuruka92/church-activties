# Parish Information Hub: Snowflake Demo

A small, **fully simulated** demonstration of how information from different parish functions
(Mass schedule, attendance, offertory, parishioner records, special donations, surveys, annual
plans and budgets, events and reports, regions) can be collected, standardised, related and
prepared for reporting in **Snowflake**.

> **All data is fictional.** Names, families, regions, events, donations and amounts are generated by a
> program. Nothing comes from a real parish, and the map geometry is deliberately not a real place.
> Business content (data values, labels, view columns, the data dictionary) is in **Bahasa
> Indonesia**. Technical documentation and code comments are in English.

This repository covers **Phase 1** (data model, synthetic data, load scripts, validation, documentation) and
**Phase 2** (a Streamlit dashboard in Bahasa Indonesia) of [CLAUDE.md](CLAUDE.md).

> **New to Snowflake?** Follow the [starter guide](docs/STARTER_GUIDE.md). It takes you from creating a free account,
> through connecting GitHub and running the setup, to the running dashboard, with no prior knowledge needed.

The data covers **five and three-quarter years** (January 2021 to a fixed snapshot on 30 September
2026), so it can show trends and forecasts. Four ready-made analysis stories are described in
[docs/USE_CASES.md](docs/USE_CASES.md): income versus outcome with a three-year forecast, what moves the
offertory, unforeseen events (rain, haze, ash) and forecast bias, and whether the Lent and Advent
donations cover the Easter and Christmas celebrations.

## What you get

| Item | Count |
|---|---|
| Schemas | `MASTER_DATA`, `DATA_OPERASIONAL`, `ANALISIS` in database `PUSAT_INFORMASI_PAROKI` |
| Tables | 38 (18 master and reference, 20 operational) |
| Summary views | 22, aggregates only |
| Synthetic rows | about 13,900, six regions, 18 communities, nine parish sections, 227 households, 653 people |
| Validation checks | 320 result rows, returned as one result table |
| Dashboard | One Streamlit file, 8 pages in Bahasa Indonesia, reads only the `ANALISIS` views |

The nine business domains and their tables are listed in
[docs/DATA_MODEL.md](docs/DATA_MODEL.md). Column meanings, grain and allowed values are in the
Bahasa Indonesia [docs/DATA_DICTIONARY.md](docs/DATA_DICTIONARY.md). The use-case guide
[docs/USE_CASES.md](docs/USE_CASES.md) explains how the data was shaped and what each view shows.

## Before you start

You need:

1. A Snowflake account, for example the free trial, and a browser to open **Snowsight** (the Snowflake web interface).
2. A **role** that may create a database. In a trial account `ACCOUNTADMIN` and `SYSADMIN` both work.
3. A running **warehouse** (the compute that runs queries). The smallest size is enough. The project
   does not assume a warehouse name, so select whichever one your account has.

You do **not** need to install anything to run the setup. Python is only needed if you want to
change or regenerate the data.

## Quick start: everything in one go

1. Sign in to Snowsight and open a new **SQL worksheet** (menu labels vary a little between Snowflake releases; see [docs/SETUP_SNOWFLAKE.md](docs/SETUP_SNOWFLAKE.md)).
2. At the top right of the worksheet, choose your **role** and **warehouse**.
3. Open [`sql/full_setup.sql`](sql/full_setup.sql) on GitHub, use **Copy raw file**, and paste the whole text into the worksheet.
4. Click the small arrow next to the blue **Run** button and choose **Run All**.
5. When it finishes, the worksheet shows the result of the last statement, the validation table. Check the first two rows:

   | CHECK_NAME | FOUND_COUNT | RESULT |
   |---|---|---|
   | Checks with result FAIL | 0 | PASS |
   | Checks with result WARN | 1 | PASS |

   The single expected warning is a deliberately inconsistent report (see [Reading the validation result](#reading-the-validation-result)).

`full_setup.sql` is steps 0 to 6 joined together (about 1.8 MB). It never drops or deletes anything, and it is safe to run again. If your browser struggles with a file that size, use the step-by-step route below. The largest step file is about 420 KB.

## Or run it one step at a time

Each file starts by selecting the database, so you can open any of them in its own worksheet. Run
them **in this order**:

| Step | File | What it does | Re-runnable |
|---|---|---|---|
| 0 | [`sql/00_setup.sql`](sql/00_setup.sql) | Shows your role and warehouse. Changes nothing. | yes |
| 1 | [`sql/01_create_schemas.sql`](sql/01_create_schemas.sql) | Creates the database and three schemas. | yes |
| 2 | [`sql/02_create_tables.sql`](sql/02_create_tables.sql) | Creates the 38 tables with keys and Bahasa Indonesia comments. | yes (`IF NOT EXISTS`) |
| 3 | [`sql/03_load_reference_data.sql`](sql/03_load_reference_data.sql) | Loads reference and master data (`MASTER_DATA`). | yes (`MERGE`) |
| 4a | [`sql/04a_load_mass_history.sql`](sql/04a_load_mass_history.sql) | Unforeseen-event log, Mass occurrences, attendance. | yes (`MERGE`) |
| 4b | [`sql/04b_load_offertory.sql`](sql/04b_load_offertory.sql) | Offertory collections. | yes (`MERGE`) |
| 4c | [`sql/04c_load_parishioners.sql`](sql/04c_load_parishioners.sql) | Households, people and their assignments. | yes (`MERGE`) |
| 4d | [`sql/04d_load_surveys.sql`](sql/04d_load_surveys.sql) | Survey respondents, answers and aggregates. | yes (`MERGE`) |
| 4e | [`sql/04e_load_plans_and_events.sql`](sql/04e_load_plans_and_events.sql) | Annual plans, budgets, expenditure, events, reports. | yes (`MERGE`) |
| 4f | [`sql/04f_load_donations.sql`](sql/04f_load_donations.sql) | Donation campaigns, household gifts, regional summaries. Needs 4c and 4e. | yes (`MERGE`) |
| 5 | [`sql/05_create_views.sql`](sql/05_create_views.sql) | Creates the 22 views in `ANALISIS`. | yes (`CREATE OR REPLACE VIEW`) |
| 6 | [`sql/06_validate_data.sql`](sql/06_validate_data.sql) | Read-only checks. Run it whenever you like. | yes |
| 99 | [`sql/99_reset_demo.sql`](sql/99_reset_demo.sql) | **Destructive.** Every statement is commented out. Not part of the setup. | n/a |

Steps 3 and 4a to 4f use `MERGE` on the primary key, so running them again updates existing rows and
adds missing ones. They never create duplicates and never delete anything. Run the 4 files in the
order shown, since a later file refers to rows loaded by an earlier one. Run step 5 before step 6,
because the validation also checks that every view works.

The operational data is split into six files only to keep each one small enough to paste into a
browser worksheet. The split follows the business areas; there is no other meaning in it.

Prefer the command line? See [docs/SETUP_SNOWFLAKE.md](docs/SETUP_SNOWFLAKE.md) for Snowflake CLI
and SnowSQL commands.

## The dashboard

After the setup, create the dashboard from [`app/streamlit_app.py`](app/streamlit_app.py): in Snowsight choose
**Projects, Streamlit, + Streamlit App**, paste the file into the editor, and run it. The starter guide has the
screens ([part 8](docs/STARTER_GUIDE.md#8-create-the-dashboard)), including how to create it from a connected
GitHub repository. What each page shows and why it was designed that way is in
[docs/DASHBOARD.md](docs/DASHBOARD.md); developer notes are in [app/README.md](app/README.md).

The dashboard runs inside Snowflake, needs no installation, and reads only aggregate views. Every page carries the
"DATA SIMULASI" notice, and no page ranks regions, communities or Mass sessions.

## Try it

After the setup, run any of these in a worksheet (select the database first, or keep the
fully qualified names):

```sql
-- Attendance per month and Mass session
SELECT NAMA_PERIODE, NAMA_MISA, JUMLAH_MISA_TERLAKSANA, TOTAL_UMAT, RATA_RATA_UMAT_PER_MISA
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.KEHADIRAN_MISA_BULANAN
ORDER BY TAHUN, BULAN, NAMA_MISA;

-- Month-to-month trend of the average attendance
SELECT NAMA_PERIODE, TOTAL_UMAT, RATA_RATA_UMAT_PER_MISA, PERUBAHAN_PERSEN_RATA_RATA
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.TREN_KEHADIRAN_PERIODE
ORDER BY TAHUN, BULAN;

-- Planned budget versus actual spending per section (programs that were carried out)
SELECT NAMA_SEKSI, ANGGARAN_PROGRAM_TERLAKSANA, REALISASI_PROGRAM_TERLAKSANA, PERSEN_TERPAKAI_PROGRAM_TERLAKSANA
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.ANGGARAN_VS_REALISASI_SEKSI;

-- How complete are the post-event reports?
SELECT NAMA_SEKSI, JUMLAH_TERLAKSANA, JUMLAH_LAPORAN_FINAL, JUMLAH_LAPORAN_DRAF_ATAU_REVISI, JUMLAH_BELUM_ADA_LAPORAN
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.KELENGKAPAN_LAPORAN_PER_SEKSI;

-- One survey question with counts and percentages
SELECT KATEGORI_JAWABAN, JUMLAH_RESPONDEN, PERSENTASE_JAWABAN
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.HASIL_SURVEI
WHERE ID_PERTANYAAN = 'PRT-0101'
ORDER BY NOMOR_OPSI;
```

The use-case views (income versus outcome, forecast, unforeseen events, community donations,
Easter and Christmas break-even) have ready-to-run queries and the expected results in
[docs/USE_CASES.md](docs/USE_CASES.md). For example:

```sql
-- Offertory versus programme spending, with a straight-line projection
SELECT TAHUN, JENIS_DATA, KOLEKTE_TREN, PENGELUARAN_TREN, TREN_PENGELUARAN_MELEBIHI_KOLEKTE
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.PROYEKSI_PEMASUKAN_PENGELUARAN
ORDER BY TAHUN;

-- What did each unforeseen event cost the offertory (a rough estimate)?
SELECT NAMA_PERISTIWA, TINGKAT_GANGGUAN, PERSEN_KEHADIRAN_TERHADAP_HARAPAN,
       PERSEN_KOLEKTE_TERHADAP_HARAPAN, PERKIRAAN_KOLEKTE_YANG_TIDAK_DITERIMA
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.DAMPAK_PERISTIWA_LUAR_BIASA
ORDER BY TANGGAL_MULAI;

-- Lent and Advent gifts versus the cost of Easter and Christmas
SELECT TAHUN, NAMA_KESEMPATAN, TOTAL_SUMBANGAN, BIAYA_AKTUAL, STATUS_TITIK_IMPAS
FROM PUSAT_INFORMASI_PAROKI.ANALISIS.TITIK_IMPAS_KAMPANYE
ORDER BY TAHUN, NAMA_KESEMPATAN;
```

All 22 views are described in the data dictionary. Every view has a `SUMBER_DATA` column that says
`Data simulasi (fiktif)`. No view ranks regions, communities or Mass sessions.

## Reading the validation result

[`sql/06_validate_data.sql`](sql/06_validate_data.sql) returns one table with these columns:

| Column | Meaning |
|---|---|
| `CHECK_GROUP` | Area: `STRUCTURE`, `KEYS`, `REFERENCES`, `VOCABULARY`, `NUMBERS`, `DATES`, `MASS`, `PARISHIONERS`, `GOVERNANCE`, `DONATIONS`, `DATASET`, `EVENTS`, `PLANNING`, `SURVEYS`, `VIEWS` |
| `CHECK_NAME`, `OBJECT_NAME` | What was checked and on which table or view |
| `FOUND_COUNT` | Number of offending rows (or the row count for `STRUCTURE`) |
| `RESULT` | `PASS`, `FAIL` (the data is wrong), `WARN` (look at it), `INFO` (a deliberate demo situation, for interpretation) |

For the bundled data the correct outcome is **0 FAIL and exactly 1 WARN**. The warning is
`Report participants differ from the event`: one post-event report has the status *Perlu Revisi*
and a participant count that does not match its event, on purpose. The `INFO` rows count the
situations that the demo is meant to contain: attendance waiting for validation, offertory not yet
reconciled, postponed or cancelled plans, completed events without a report, partly used budgets,
a survey without responses, attendance records tied to unforeseen events, and donation campaigns
that are still planned or waiting for validation.

Snowflake does not enforce primary or foreign keys on standard tables, so the script checks
duplicate identifiers and orphaned references explicitly.

## Safety and idempotency

* Steps 0 to 6 and `full_setup.sql` never drop, truncate or delete anything.
* Step 2 uses `CREATE TABLE IF NOT EXISTS`. It does **not** change an existing table. If you edit a table definition later, reset the demo (below) and run the setup again.
* **If you already ran an earlier version of this repository in Snowflake**, reset it first. The tables for donations, attendance and regions changed (a new event log, campaigns, household gifts, an economic profile), and `IF NOT EXISTS` will not alter the old ones. See `sql/99_reset_demo.sql`, option B or C.
* [`sql/99_reset_demo.sql`](sql/99_reset_demo.sql) is the only destructive file. All its statements are commented out, it names only the demo objects, and it is excluded from `full_setup.sql`.
* No credentials, tokens or account names are stored anywhere in this repository. Keep Snowflake connection files (`config.toml`, `connections.toml`, key files) outside the repository. `.gitignore` blocks the common ones.

## Using a different database name

The database name appears only in the `USE DATABASE ...;` line at the top of each file, in the
`CREATE DATABASE` statement of step 1, and in the commented `DROP` statements of the reset script. To
use another name (for example to try the demo next to something else), replace every occurrence of
`PUSAT_INFORMASI_PAROKI` in the text you paste into the worksheet. All other statements use only the
schema names, so nothing else needs to change.

## Changing or regenerating the data

The committed SQL is generated by a Python script that needs **only the standard library**
(Python 3.11 or newer; verified on 3.11, 3.12 and 3.13).

```bash
python scripts/generate_mock_data.py            # rewrite sql/03, 04a-04f, 06, 99, full_setup.sql and the data dictionary
python scripts/generate_mock_data.py --check    # fail if a committed generated file is stale
python scripts/generate_mock_data.py --csv-dir data/generated   # optional CSV export (ignored by Git)
```

The data is reproducible: the random seed and the snapshot date (2026-09-30) are fixed in
[`scripts/mockdata/config.py`](scripts/mockdata/config.py). The assumptions behind the analysis
stories (attendance and offertory trends, payday effect, event list, programme spending, donation
totals, economic profile of the communities) are plain tables in the generator modules; the guide
[docs/USE_CASES.md](docs/USE_CASES.md) lists where each one lives. The table definitions in
`sql/02_create_tables.sql` are the single source of truth. The generator reads them, and the data
dictionary is built from their comments.

Run the tests:

```bash
python -m unittest discover -s tests -v          # the SQL and dashboard tests skip themselves without the packages below
pip install -r tests/requirements.txt            # optional: DuckDB, sqlglot, Streamlit, Altair, pandas
```

## Verification status: please read

What has been **tested locally**:

* The generator is deterministic and its output is identical on Python 3.11, 3.12 and 3.13.
* The automated tests pass. They cover the DDL, data integrity, privacy and language rules, and that the checks can actually fail.
* The real SQL files (tables, loads, views, validation, and the all-in-one script) were executed against **DuckDB**, a different database engine used as a stand-in. Loading twice does not duplicate rows, the validation reports 0 FAIL and 1 WARN, and each of 34 deliberately corrupted copies of the data was detected.
* The analysis stories are tested as properties of the views (offertory growth slows, spending overtakes the offertory trend, payday and attendance effects, every event shows a dip, Christmas goes into deficit while Easter stays in surplus, mean differs from median in the large-donor communities). The figures in [docs/USE_CASES.md](docs/USE_CASES.md) come from that local run.
* Every SQL file parses with the Snowflake grammar of `sqlglot` (a syntax lint, not Snowflake).
* The dashboard was driven page by page with Streamlit's test runner against the same DuckDB stand-in, and viewed in a headless browser in light and dark themes. It was also run on an older stack (Python 3.11, Streamlit 1.35, Altair 4.2) and the current one (Streamlit 1.66). It reads only allowed views, and a test fails if a page shows ranking words.

What has **not** been done: **nothing has been executed in Snowflake.** No connection to Snowflake
was made while building this repository, so successful loading in your account has not been
verified. Points most worth watching on the first real run:

1. `COMMENT` placed after `NOT NULL` in column definitions (`sql/02`).
2. The `MERGE ... USING (SELECT ... FROM (VALUES ...) AS v (...))` form (`sql/03`, `sql/04a`-`04f`), with up to 1,000 rows per statement.
3. Compile time of the single validation statement with about 300 `UNION ALL` branches (`sql/06`).
4. Functions used by the new views that DuckDB implements slightly differently: `MEDIAN`, `CORR`, `REGR_SLOPE`, `REGR_INTERCEPT`, `REGR_R2`, `DATEADD`, `DATEDIFF`, `MOD`, `LEAST` (`sql/05`).
5. Whether Snowsight accepts the 1.8 MB `full_setup.sql` in one paste. The step files are the fallback.
6. How the dashboard behaves inside Streamlit in Snowflake (Streamlit version and runtime, theme detection, first-start time).
7. The Git integration statements, `EXECUTE IMMEDIATE FROM` on the larger files, and `CREATE STREAMLIT ... FROM` in the starter guide. They follow Snowflake's published documentation and were not run in an account.
8. Menu labels in Snowsight, which change between releases.

If anything fails, the error message names the statement. Report it so the generator can be fixed;
the generated files should never be hand-edited.
